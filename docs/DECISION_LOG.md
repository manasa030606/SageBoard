| D43 | Phase 5 scope | **Final** (2026-11-14, owner) | Phase 5 = the full agentic core (12 responsibilities as LangGraph nodes, SQL Guard, error recovery, analysis, charts, insights, verification, final response) — the former roadmap phases 5–7. Remaining items move to Phases 6–7 | DEVELOPMENT_ROADMAP §2 |
| D44 | Separate Error Recovery node | Implemented | `recover_error` classifies the failure in code (Guard code / SQLSTATE → category + hint), gathers error-specific schema, regenerates, and sends the new SQL back through the Guard. ≤ 3 attempts per step; identical SQL is rejected as `REPEATED_QUERY` | AGENT_WORKFLOW §6 |
| D45 | Tool calling via structured outputs | Implemented | `retrieve_schema` is a bounded loop where each model turn is a validated `SchemaAction`; tools run in code; errors return as observations. Same behaviour on every provider | AGENT_WORKFLOW §6 |
| D46 | Clarification is a conversation turn | Implemented | A run that needs clarification ends `awaiting_input`; the next message re-runs the original question with `clarification_answer`. No LangGraph checkpointer/interrupt (no extra Postgres driver, survives restarts) | AGENT_WORKFLOW §7 |
| D47 | Grounding is authoritative, the judge is reject-only | Implemented | Numbers must match cited facts/cells within display rounding; the model judge can only reject. Still-rejected insights are removed after 2 rounds and listed; the final summary is grounding-checked with a deterministic fallback | AGENT_WORKFLOW §6 |
| D48 | In-process run manager | Implemented | Runs are asyncio tasks in the API (ADR-0004), with a concurrency cap and cancel at node boundaries. Node events are persisted live in `agent_node_runs` (migration 0005); runs left `running` by a restart are marked `failed: INTERRUPTED` | ADR-0004 |
| D49 | Agent cost controls | Implemented | Per run: ≤ 30 model calls, ≤ 14 SQL executions, 180 s deadline, ≤ 5,000 result rows (all configurable). Per user: 30 questions/hour | API_SPECIFICATION §11 |
| D50 | Free LLM for development | **Final** (2026-11-14, owner) | Google Gemini via Google AI Studio's free tier: `LLM_PROVIDER=google`, `LLM_MODEL=gemini-3.8-flash`, `GOOGLE_API_KEY` (backend `.env` only). No paid usage: key from a project without billing; no automatic provider/model/tier switching. Client-side pacing (`LLM_REQUESTS_PER_MINUTE`), a daily model-call cap counted from live traces (`LLM_DAILY_REQUEST_LIMIT`, midnight Pacific), Google 429s classified (per-minute → wait `retryDelay`; daily quota / `limit: 0` / bad key → stop the run with the reason). Free-tier prompts may be used by Google to improve its products, so use non-sensitive data | [ADR-0006](adr/0006-provider-agnostic-llm-layer.md) |
| D51 | Phase 6 = SQL safety, execution & self-correction | **Final** (2026-11-15, owner) | Owner-defined scope (the former Phase 7 hardening): unsafe queries (writes, DDL, other schemas, server functions, stacked statements) and permission errors are **never retried** — recovery is for honest mistakes only; SQLSTATE 25006 (DB read-only defence fired) is treated as a Guard bug, not retried. Design caps enforced: recursive CTEs rejected, ≤ 6 joins, subquery depth ≤ 4. EXPLAIN cost gate (`EXECUTOR_MAX_PLAN_COST`, default 5M units, recoverable `too_expensive`). In-flight SQL cancelled via asyncpg task cancellation (`pg_cancel_backend` mechanism). Hypothesis fuzzing + Guard-bypass isolation tests. Real-model evaluation moves to Phase 7 | [SQL_SAFETY.md](SQL_SAFETY.md) |
| D52 | Phase 7 = result analysis, insights, visualizations & frontend integration | **Final** (2026-11-15, owner) | Owner-defined scope, superseding the roadmap's "real-model evaluation" slot (evaluation now runs continuously and gets a dedicated pass before deployment). Backend: chart vocabulary extended to `horizontal_bar`, `pie`/`donut`, `scatter`, `histogram` (all validated against real step results, falling back to a table with the reason recorded); `FinalResponse.follow_up_questions` (≤ 3, grounding-checked — a suggestion with an ungrounded number is dropped, not rewritten). Frontend: the analyst workspace switches from recorded demo scenarios to the live API (conversations, polling run cards with live trace + cancel, charts via Recharts incl. pie/donut/scatter/histogram/KPI tiles, evidence chips that highlight source rows, per-step SQL + attempts, follow-up chips, save-as-report). Pipeline proven end-to-end on two datasets (demo e-commerce + an uploaded CSV with a different schema) with multiple questions | [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md) |
| D53 | Conversation memory is deterministic, per conversation, relevance-gated | **Final** (2026-11-15, owner spec) | Each finished turn stores a compact memory record in `analysis_sessions.memory` (JSONB, migration 0006), built **by code** from the stored understanding, result and summary — no model call, so it cannot invent anything. A new question is shown at most 3 earlier turns of *its own conversation*: the previous turn when the wording is a follow-up ("and…", "compare it…", pronouns, very short), otherwise turns whose topic words overlap (≥ 34% of the question's topic words) with the question; scan window 20 turns, 3,500-character budget. Candidates are fetched with owner, dataset and conversation in the WHERE clause, so another user's, conversation's or dataset's turns are never candidates; a turn recorded against an older dataset version keeps its shape but drops its numbers. `understand_query.v2` teaches reference resolution ("compare it with last month" → restated standalone question) and forbids carrying numbers forward. Memory across conversations is deliberately not built (it would be the main isolation risk) | [AGENT_WORKFLOW.md §7](AGENT_WORKFLOW.md) |
| D54 | History reuses what runs already store | **Final** (2026-11-15) | The owner's "save question, dataset, status, plan, SQL, results, insights, timestamp" was already satisfied by `analysis_sessions` (+ `result` JSONB) and `query_executions`; Phase 8 adds no duplicate tables. `GET /history/sessions` now returns `HistoryItem` (dataset and conversation names, answer snippet, finding and query counts, newest report id — counts computed in SQL so the stored result is never loaded for a list) and searches question, answer **and** dataset name. Reopening and continuing are deep links (`/app/analyst?conversation=&session=`) onto the same conversation, so a follow-up uses the memory in D53 | [API_SPECIFICATION §6](API_SPECIFICATION.md) |
| D55 | Reports: snapshot v2, server-rendered PDF, numbers re-checked at read time | **Final** (2026-11-15) | A report copies everything from the stored result when saved (dataset tables, methodology, SQL per step, verified findings, recommendations, chart data, limitations); nothing is regenerated and no model is called. The PDF is rendered on the server with reportlab (pure Python, bundled Bitstream Vera font, vector charts, `asyncio.to_thread`) — all text is XML-escaped and glyph-sanitised. "Numbers match the stored results" is enforced by the same grounding engine the agent uses, run when a report is **read or exported** (not just saved): a user-edited summary with a number absent from the stored rows/facts is flagged in the API, the PDF and the UI. Old (v1) reports still open and export; they say what they lack | [API_SPECIFICATION §7](API_SPECIFICATION.md) |
| D56 | Two evaluation modes, labelled | **Final** (2026-11-15) | **Oracle** mode replays each case's reference SQL through the real Guard, executor, analysis engine, verification, persistence and API; it measures the pipeline and is always labelled "not model accuracy". **Live** mode uses the configured real provider, is resumable, honours the daily model cap and stops on quota/auth errors; only it may produce model-accuracy claims. The build sandbox had no model access, so no live numbers exist yet. |
| D57 | Ground truth computed independently of SQL | **Final** (2026-11-15) | Expected results come from plain-Python functions over the seeded generator, and every reference query is checked against them on PostgreSQL (`test_eval_dataset.py`). The comparator is value-based (columns and order of columns free, integers exact, other numbers within 0.01 or 0.01 %, percent versus fraction not forgiven) and is itself unit-tested. |
| D58 | Sensitive result values never reach the model | **Final** (2026-11-15) | Result columns marked `is_sensitive` are replaced by `«redacted»` in all five model-bound payloads, and the payload names the hidden columns (SECURITY_DESIGN §6, which already required it; the implementation had a gap found by eval case X02). Matching is by result column name, so an aliased column escapes (documented limit). Stored results shown to the owner are unchanged; masking them in the UI is left to the owner. |
| D59 | Executor pins the session time zone to UTC | **Final** (2026-11-15) | `SET LOCAL TIME ZONE 'UTC'` in every read-only transaction, so month and day boundaries do not depend on server or role defaults. Regression test uses an Asia/Kolkata default. |
| D60 | `CARTESIAN_JOIN` Guard rule implemented | **Final** (2026-11-15) | A join of two real tables with no condition (no `ON`/`USING`, `ON TRUE`, no column-equals-column in `WHERE`) is rejected as a recoverable Guard error. A `CROSS JOIN` against a subquery or CTE stays allowed (share-of-total pattern). Reason: measured, the EXPLAIN cost gate alone let two-table cross joins run. |
| D61 | Browser tests use the real stack with the oracle model | **Final** (2026-11-15) | Playwright runs the real Next.js app against the real FastAPI + PostgreSQL, with the model replaced by the oracle (`evals/e2e_server.py`, test databases, backend on 8100). The existing frontend on 3001 is reused (`reuseExistingServer`); because `NEXT_PUBLIC_*` values are fixed when `next dev` starts, `e2e/fixtures.ts` reroutes the browser's calls from the app's API URL (8000) to the test backend instead. No API key, repeatable. Chrome is selected with `PLAYWRIGHT_CHROME_PATH` or `playwright install chromium`. The Save-as-report test was verified to fail when the earlier GET/POST bug is reintroduced. |
